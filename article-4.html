How well do LLMs write GPU kernels for Apple Silicon?

A benchmark, three months of measurements, and one small fine-tune still running on a Kaggle P100 as of this writing.

Erika Goh Jul 2026 12 min read

Why I built this

So the thing about GPU programming is that CUDA has been the default for fifteen years. If I ask a frontier LLM to write me a fast matmul, what comes back is CUDA — not because I asked for it, but because NVIDIA's toolchain is the water these models swim in. Everything on the public internet that touches "GPU kernel" has __global__ in it somewhere.

But CUDA is NVIDIA-only. My Mac runs Apple Silicon, which uses Metal — a related-but-not-identical GPU programming model with its own shading language (MSL, the Metal Shading Language). Apple's own libraries — MPS, Core ML, PyTorch's MPS backend — all dispatch Metal under the hood.

For my own learning, I wanted to know: how well do LLMs actually generalize from CUDA to Metal? Not "can they emit Metal syntax" — they can, if you ask nicely — but "when the Metal answer diverges from the CUDA answer, do they cross the gap correctly?"

That question turned into MSL-Bench. It's 60 numerical operations, judged end-to-end: the LLM writes MSL, my harness compiles it with the real Xcode toolchain, verifies it against a PyTorch MPS reference, and times it with GPU timestamps. The number that comes out is fast_p — the fraction of problems where the model produced a kernel that (a) compiles, (b) matches the reference numerically, and (c) runs at least p× the MPS reference speed. fast_0 is "correct," fast_1 is "as fast as Apple's own kernel," fast_2 is "twice as fast."

If you only remember one thing from this: every model I tested nails elementwise operations and falls off a cliff the moment the problem requires threadgroup-level coordination. The height of the cliff varies. The cliff itself is universal.

That's the story. The rest of this is how I got there — and one thing I'm running right now to see if it's fixable.

What "writing Metal" actually looks like

Quick minute on what MSL is and why it isn't just "CUDA with different keywords" — this matters for the whole benchmark. A Metal compute kernel is a function that runs on the GPU across many threads in parallel: 

kernel void vector_add(device float *a [[buffer(0)]],
                       device float *b [[buffer(1)]],
                       device float *out [[buffer(2)]],
                       uint id [[thread_position_in_grid]]) {
    out[id] = a[id] + b[id];
}

This is a T1 (elementwise) kernel. Buffer bindings, per-thread ID, one line of math. Every model I tested wrote this correctly.

CUDA's equivalent, side by side:

__global__ void vector_add(float *a, float *b, float *out) {
    int id = blockIdx.x * blockDim.x + threadIdx.x;
    out[id] = a[id] + b[id];
}

You can see the transfer at once: the shape is identical, the syntax has moved. This is the easy case. The model pattern-matches "thread ID → indexed load → store" and gets it right.

The problem shows up the moment threads have to cooperate. Say I want to compute the sum of each row in a 262144×256 matrix. In CUDA: 

__shared__ float scratch[256];
scratch[threadIdx.x] = x[row * K + threadIdx.x];
__syncthreads();
// ... tree reduce ...

The Metal version looks almost identical:

threadgroup float scratch[256];
scratch[lid] = x[row * K + lid];
threadgroup_barrier(mem_flags::mem_threadgroup);
// ... tree reduce ...

Notice threadgroup_barrier(mem_flags::mem_threadgroup). CUDA's __syncthreads() has no arguments. Metal's barrier takes a memory scope flag — mem_threadgroup, mem_device, mem_texture, or an OR of them — because Metal's memory model is more explicit about which pool of memory is being fenced. Pick the wrong flag and your kernel still compiles, still runs, still produces correct output — and pays a measurable perf cost on every reduction step. I'll come back to this exact bug; it's costing 7% on p101_row_sum in the wild.

This is the kind of thing that separates "I've seen Metal syntax" from "I've written Metal." And it turns out to be surprisingly hard for LLMs to just infer.

The benchmark itself

MSL-Bench has 60 problems in four tiers:

The tiering isn't just difficulty — it's calibrated around what MSL-specific patterns each problem forces the model to use. T1 problems could be written in almost any C-like GPU language. T2+ problems specifically require Metal idioms that don't map 1:1 from CUDA. That's a deliberate choice: the benchmark is measuring transfer competence, not algorithm discovery.

Every candidate kernel goes through the same pipeline:

  1. Compile — write the MSL to disk, invoke xcrun metal → .metallib. If it fails, capture the compiler diagnostic verbatim (that diagnostic gets fed back to the model on the next repair attempt).
  2. Execute — a small Swift runner binds input buffers, dispatches with the grid shape the spec requires, and reads GPU timestamps off the command buffer.
  3. Verify — output tensors are allclose'd against a PyTorch MPS reference. NaN/Inf is an automatic fail; per-problem tolerances are set to what MPS-vs-double differs by.
  4. Time — 3 warmup runs, then median of 10 timed runs. Runs with IQR > 15% of median are flagged as thermally noisy.

The whole thing runs on the Mac I already own. Free-tier LLM APIs (Groq, Gemini) plus optional local Ollama mean I can run a full sweep without paying a cent.

The T1 → T2 cliff

Here's the headline. One-shot sweeps on four models:

Three things pop out.

Metal elementwise fits in an 8B model. Both 8B and 70B Llamas hit 100% on T1. Whatever an LLM needs to know about MSL to write out[i] = f(x[i]) is compact enough that the small model already has it. The bigger model's edge starts at T2 — that's where MSL-specific patterns begin to matter.

The cliff is universal but variable-height. Every non-reasoning model drops sharply between T1 and T2. Llama-3.1-8b drops 93 points; Gemini drops 72; gpt-oss-120b — the strongest model in my set — still drops 46. This isn't any single provider getting Metal "wrong." It's the domain: T1 is a C-math translation, T2 requires knowing Apple's specific memory model.

Reasoning models have an inverted profile. qwen3-32b is the only model in my set that failed T1 — 3 out of 15. Its dominant failure mode was using thread_position_in_grid as a free variable (CUDA-style) instead of a parameter attribute. Reading its <think> blocks, you can watch it derive the wrong syntax from adjacent-language knowledge. But qwen3 is also the only model that got any T3 problem correct. Reasoning appears to hurt on syntax-shape problems and help on algorithm-shape problems — even while being dramatically worse overall.

So I ran a follow-up specifically to test this. If truncated <think> was the bottleneck (a plausible hypothesis — reasoning tokens compete with kernel-emit tokens under a shared max_tokens=4096 budget), correctness should improve when I gave the model more room. I bumped max_tokens from 4096 to 5200, the ceiling under Groq's free-tier per-minute cap for qwen3.

It got worse. Zero confirmed correct at mt=5200 vs 5 correct at mt=4096. And I could see the mechanism at kernel level. On p003_elementwise_mul, mt=4096 wrote: 

uint id [[thread_position_in_grid]]     // verifies correct

mt=5200, on the same problem with ~1100 more reasoning tokens, wrote: 

uint id [[thread_index_in_grid]]        // compile fail

thread_index_in_grid is not a real MSL attribute. qwen3, given more reasoning budget, derived itself off a correct answer. Extra tokens didn't buy access to the right pattern; they bought more elaborate wrong derivations from adjacent languages. This is the clearest evidence I've seen personally for "reasoning can hurt when the answer is memorized syntax."

Anatomy of the LLM-vs-MPS speed gap

Getting a T2 kernel correct isn't the same as getting it fast. On p101_row_sum, Groq's llama-3.3-70b wrote a kernel that verified correctly, then ran at 0.42× MPS speed. It compiled, it ran, it did the right thing — and it was 2.4× slower than Apple's own kernel doing the same job.

So I hand-patched that kernel four ways to figure out where the gap actually lives. The problem is memory-bound (input is 268 MB), so effective bandwidth is the honest number:

Three layers of cost, each measured:

Layer 1 — Barrier-flag confusion (~7%). Groq wrote threadgroup_barrier(mem_flags::mem_device) when the reduction only touches threadgroup memory. Apple's compiler partially elides the redundant device-scope fence, but not entirely. This is the exact CUDA→MSL transfer failure I flagged at the start: __syncthreads() has no flag parameter, so the model doesn't know a flag is load-bearing.

Layer 2 — Missing MSL idioms (~8%). Groq's algorithm was correct-but-generic — a halving-tree reduce over threadgroup memory. Metal has SIMD-group intrinsics (simd_shuffle_down) that let you reduce inside a SIMD group using registers only, no shared memory and no barriers. Rewriting the reduction that way saved another 8%.

Layer 3 — Bandwidth utilization (~50%). Even my hand-tuned kernel peaks at 90.5 GB/s vs MPS's 175. A float4-load variant made no difference — Apple's memory subsystem already coalesces adjacent scalar loads into cache-line transactions. Transaction count isn't the knob.

Layer 3 breaks into two sub-layers, and this is where the benchmark gets honest about itself:

  • 3a. Model-recoverable (~15% of the total gap). Small extra micro-optimizations a better kernel-designing LLM could reach for under the spec's constraints.
  • 3b. Baked into the spec's launch config (~35% of the total gap). The problem spec fixes the launch: one threadgroup per row, 256 threads per group. Under that constraint, ~90 GB/s appears to be the ceiling. MPS isn't bound by the spec — it picks its own launch — and uses that freedom to run at ~2× the throughput.

I found this while writing the report, and it means that under the current benchmark design, no candidate kernel can close the last 35% of the gap on this problem, however well designed. That's a benchmark artifact, not a model-quality issue. Worth flagging honestly. I'll come back to what to do about it.

Can repair@5 unstick the T2 wall?

The second thing I wanted to test: if I give the LLM its own compile diagnostics back and let it try again up to 5 times, how much of the T2 wall does it break through?

Answer: not much, and in an informative way. On the 17 problems where I could run both one_shot and repair@5 before Groq's daily quota killed the sweep, both modes scored 14/17. Repair added zero new correct kernels. What it changed was the failure mode on two T2 problems: 

p102_row_max      one_shot: compile-fail  →  repair@5: verify-fail
p104_row_softmax  one_shot: compile-fail  →  repair@5: verify-fail

The compile diagnostics got the model past MSL syntax errors, but 5 rounds of "wrong answer, max_abs_err=X" feedback wasn't pointed enough to drive it from wrong-numerically to right-numerically. Mapped onto the layered analysis from the previous section:

  • Layer 1 errors — compile-fails. The compiler tells the model what's wrong. Repair fixes these.
  • Layer 2 errors — verify-fails. Code runs, semantics are wrong. Scalar-error feedback can't point at the specific line.
  • Layer 3 errors — slow-but-correct. Invisible to both compile and verify signals.

So the ceiling of repair@5 with only compile + scalar-correctness signal is "unstick layer-1 errors." Anything past that needs a richer feedback surface — per-element diff previews, shape-mismatch hints, or performance-vs-reference signals. That's a natural direction for a future revision.

Can models learn Metal from their own failures? (training in progress)

Everything above is measurement. What I actually want to know next is whether it's learnable — whether the failure transcripts an LLM produces on MSL-Bench are themselves sufficient training data to make a better MSL-writing LLM.

That's Phase 6, and it lives in a sibling repo called MSL-Flywheel. For my own learning, I wanted to run the whole loop end to end at least once, on free infrastructure, and see if anything moves.

The curation step extracts three kinds of training pairs from the raw MSL-Bench transcripts:

  • Type A — repair trajectory pairs. When an attempt failed, feedback was given, and the next attempt succeeded, use the (failed_kernel + compile_error → corrected_kernel) transition as the training example. Highest signal, lowest volume.
  • Type B — best-model teacher pairs. For each problem, if any run produced a correct kernel, that kernel becomes the SFT target for training weaker models. Aggregates the suite's cross-model wisdom.
  • Type C — golden kernel pairs. Hand-verified reference kernels from tests/golden_kernels/*.metal, paired with their problem prompt.

Current curated dataset (v1) is 46 pairs: 1 Type A, 33 Type B, 12 Type C. Small — deliberately. This is the minimum viable dataset to test whether the training loop works at all, not whether it produces a strong model. The tier distribution is inverted from where I want improvement (28 T1, 10 T2, 4 T3, 4 T4 — sparse where models most need help), but that's a chicken-and-egg problem: I can only turn a correct kernel into a training pair, and models rarely produce correct T3/T4 kernels.

Training setup. LoRA fine-tune of Llama-3.1-8B-Instruct — rank 16 / alpha 32, QLoRA 4-bit NF4, paged_adamw_8bit, LR 2e-4 cosine, 3 epochs. assistant_only_loss=True so the failed-kernel turn in the one Type-A pair doesn't get pulled into the loss (I would rather the model not learn to reproduce the failure before fixing it). Runs on Kaggle's free P100 tier in about 30 minutes.

Why Llama-3.1-8B specifically? Because I already have a full MSL-Bench baseline for it on Groq — 28.3% fast_0 across all 60 problems. The delta from base to fine-tuned is directly measurable using the same 60 problems, same harness, same everything. No re-normalization games.

Serving path. Adapter downloads from Kaggle, gets converted to GGUF with llama.cpp's convert_lora_to_gguf.py, and gets registered with a local ollama install via a Modelfile: 

FROM llama3.1:8b-instruct-q4_K_M
ADAPTER ./adapter-v1.gguf

Then a run_suite.py --provider ollama --model llama-3.1-8b-flywheel-v1 --mode one_shot produces a new set of records, and compare.py prints the delta. That last piece is the whole point: does the fine-tune actually move the numbers, and where does it move them?

Results section — pending. As of 2026-07-16, the Kaggle training run is queued and unblocked (Meta's Llama-3.1-8B license accepted). The delta report will land right here. What I'll be looking for, in order of aspiration: T1 speedup shifts (kernels moving from correct-but-slow to correct-and-≥MPS — evidence the model picked up Metal-specific perf idioms); T2 correctness gains (+1 to +3 correct kernels on this dataset size would be a real result); T3/T4 movement (very aspirational — only 8 of 46 training pairs are T3+T4). If the delta is zero or negative, that's also a real finding — the 46-pair dataset isn't rich enough, and the next iteration needs more sweeps to enrich the pool.

What's next, honest caveats, and links

The spec-launch cap issue is real. ~35% of the gap on some memory-bound problems is unreachable by any candidate kernel under the current benchmark design. This is a design decision I need to make deliberately before publishing anything more definitive. Three plausible fixes: let candidates propose launch configs; time against a same-launch reference instead of MPS; or reword the metric honestly as "% of achievable-under- constraint speed." I haven't picked yet.

The roster is narrow. I only ran full 60-problem sweeps on two Groq-hosted models. Adding Claude, GPT-4, Gemini Pro, and o1 when budget permits would tell me whether the cliff shape holds across the frontier or is a mid-tier phenomenon.

Local Ollama sweep still to be done. qwen2.5-coder-14b under Ollama had a 6-problem smoke test with 0/6 correct, which is not enough data. A full 60-problem local sweep needs sustained GPU load on my laptop and a thermal-safety window I haven't scheduled yet.

Three of the findings above went through self-corrections during measurement. For instance, I initially attributed all of Groq's T2 slowness to "Groq is writing the naive one-thread-per-row pattern" — until I opened the kernel and found the textbook tree reduce with a wrong barrier flag. NOTES.md in the repo has the session-by-session versions if you want to see the thinking evolve.
